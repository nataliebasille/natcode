# Lexical structure (core subset)

Item status and open questions for this file are tracked in the [lexer scorecard](scorecards/lexer.md).

Source text is UTF-8. Positions are reported as byte-offset spans plus 1-based line and column, where columns count Unicode scalar values.

## Tokens

| Category | Forms |
| --- | --- |
| Reserved keywords | Implemented: `from`, `import`, `export`. Approved, not yet implemented: `type`, `fn`, `match`. These are case-sensitive, hard-reserved words (LEX-KW-04 through LEX-KW-07). |
| Boolean literals | `true`, `false` |
| Identifiers | Unicode identifiers per UAX #31: first character is `XID_Start` or `_`; following characters are `XID_Continue`. Letters of any script (`café`, `größe`, `π`, `中文`) are allowed. |
| Wildcard | A standalone `_` is its own token, never an identifier. `_x`, `__`, and `x_` are identifiers. |
| Numbers | Decimal integers (`42`) and decimal fractions (`3.14159`), using ASCII digits only. |
| Strings | Double-quoted, single-line: `"Alice"`, `"./math"`. Any character except a line break is allowed, including non-ASCII. |
| Operators and punctuation | `=` `=>` `:` `\|` `&` `{` `}` `(` `)` `,` `.` `*` `+` |
| Comments | `// …` to end of line; `/* … */` block comments, which nest. Comments produce no tokens. Whether line breaks inside a block comment produce newline tokens is LEX-COM-04. |
| Line breaks | LF or CRLF; each is one newline token. Spaces are insignificant between tokens. |

The reserved words are recognized as keywords regardless of position; they cannot name ordinary bindings. Keyword spellings are permitted as object property names, with details of the object grammar still to be determined (PAR-OBJ-01). `if`, `else`, `elif`, and `case` are not reserved words or language control-flow constructs. `return` is not a control-flow construct or keyword. `null` is not a native literal or reserved word; absence is represented using constructors such as `None`. Further words, including `then` and generator/effect vocabulary, remain open questions (LEX-KW-03).

## Identifier normalization

Identifiers are normalized to Unicode **NFC**, so visually identical spellings (precomposed `é` versus `e` followed by a combining acute accent) name the same identifier. String literal contents are **not** normalized.

## Number rules

- A digit separator `_` may appear only **between two digits**: `1_000` and `3.141_59` are valid; `1__0`, `1_`, `1_.5`, `1._5`, and `1.5_` are errors.
- A fraction requires a digit (or a misplaced `_`) immediately after the `.`. Otherwise the number ends before the `.`: `1.` is the number `1` followed by `.`, and `1.foo` is `1`, `.`, `foo`.
- A number cannot begin with `.`: `.5` is `.` followed by `5`.
- A leading `-` is not part of a number literal, and `-` is not an operator (see LEX-OP-03).
- A number may not be directly followed by identifier characters. `42abc`, `1_a`, and `3.14x` are each a single error, as are `1e10` and `0x1F` (see LEX-NUM-05 and LEX-NUM-06).

## Strings

- Escape sequences are **not supported**. A backslash anywhere inside a string literal is an error, and it does not escape a following `"`.
- A string that reaches a line break or the end of input before its closing `"` is an error.

## Lexical errors

Any character that cannot begin a token is an error, including emoji, non-identifier symbols such as `∑` or `€`, and ASCII characters outside the operator set (for example `-`, `/`, `;`, `@`). An unterminated block comment is an error. Lexing recovers after every error and reports all diagnostics in source order.

# Broader syntax and type-system decisions

Item status and open questions for this file are tracked in the [parser](scorecards/parser.md), [types](scorecards/types.md), and [tooling](scorecards/tooling.md) scorecards.

## Code blocks and data structures

- **Code blocks are indentation-defined.** Braces `{}` are for **data structures**, not statement/function control-flow blocks.
- Match-branch, lambda, function-definition, and data-object grammars are PAR-COND-01, PAR-FN-01, and PAR-OBJ-01; block syntax is PAR-BLK-02.

The following block is **conceptual**; its lambda form is illustrative:

```natcode
x = 10
getInner = () =>
    x = x + 1
    x
result = x
```

It illustrates an indented nested scope, not a brace-delimited code block.

## Match expressions

Natcode uses one `match` keyword for both structural pattern matching and conditional branching (PAR-COND-02). It does not have separate `if`/`else` or `case` control-flow constructs.

- **Subjectful** `match expression` selects a branch by matching patterns against that subject.
- **Subjectless** `match` evaluates Boolean branch conditions in source order and selects the first true condition.
- Both forms are expressions that produce the selected branch's value.

The following forms are **illustrative**, not a finalized branch grammar (PAR-COND-01, PAR-PAT-01):

```natcode
result = match option
    Some(value) => value
    None => 0

size = match
    x > 10 => "large"
    x > 5 => "medium"
    _ => "small"
```

The exact separator syntax, allowable patterns, branch bodies, fallback rules, and exhaustiveness handling remain open.

## Declaration keywords and expression results

- `fn` introduces named function declarations (PAR-FN-02). Parameter and body syntax remain open (PAR-FN-01).
- Functions return the value of their final expression; there is no `return` statement or explicit early return (PAR-FN-03).
- `type` introduces named type declarations (PAR-TYPE-03). Constructor and generic declaration grammar remain open (PAR-TYPE-02).
- Ordinary variable bindings continue to use keyword-free `name = expression` declarations (PAR-DECL-01).

## Inference-first philosophy

Natcode seeks a TypeScript-like ergonomics with a substantially more functional model, emphasizing purity, piping, and pattern matching. These are **design goals** (see RUN-EFF-01, PAR-PIPE-01, and PAR-PAT-01).

Ordinary variable types and function return types are intended to be inferred. The optional declaration constraint `x: Type = expression` is permitted as an **assignability check** without replacing or widening the inferred type; this updates the earlier inference-only proposal.

## Union and intersection types

- `|` is type **union**.
- Simplification/consolidation of a union is permitted **only when it preserves the exact represented set of possibilities**. In particular, preserve correlations between fields and exclusions; do not merge distinct object variants in ways that admit combinations not present in the original union.
- `&` is reserved for type **intersection**, separate from `:` constraints.

For example, this union:

```natcode
{ kind: "left", value: number }
|
{ kind: "right", value: string }
```

must not be simplified into:

```natcode
{ kind: "left" | "right", value: number | string }
```

because the latter would allow a `"left"` tag paired with a `string` value, which the original type excludes. The record-type syntax here is illustrative.

See TYP-UNI-05 (difference and complement operators), TYP-CON-03 (subtyping), TYP-GEN-01 (generics), and TYP-ADT-01 (algebraic data types).

## Target directions

Natcode is intended to support a native interpreter and compilation to JavaScript, WebAssembly, C, and potentially Python (PY-TGT-01). These are project goals rather than language semantics. A shared compiler IR/runtime design and the implementation language are TOOL-ARCH-01.

# Variable declarations and identifiers

Item status and open questions for this file are tracked in the [parser](scorecards/parser.md), [resolver](scorecards/resolver.md), and [types](scorecards/types.md) scorecards.

## Declaration syntax

```natcode
identifier = expression
identifier: Type = expression
```

- No `val`, `let`, or `var` declaration keyword is required.
- Initializers are **mandatory**; `x: number` alone is invalid.
- `:` is an optional **assignability constraint**. The initializer's inferred type must be equal to or assignable to the declared type.
- A constraint **does not widen** or overwrite the inferred type. Thus `x: number = 42` still has inferred type `42`.
- The `&` operator is reserved for type **intersections**, not type constraints.

## Immutability, redeclaration, and scope

Each declaration creates a **new immutable binding**. Reusing the same identifier, including in the same scope and with an unrelated type, is valid. The newest visible binding shadows earlier bindings; it never mutates them.

```natcode
x = 10
x = x + 5           // initializer sees previous x; new x = 15
x: string = "hi"    // new binding; previous x remains immutable
```

A declaration's initializer resolves a same-name reference to the **previously visible** binding. This holds both for a same-scope redeclaration and when a declaration shadows a binding in an outer lexical scope.

```natcode
x = 10
getInner = () =>
    x = x + 1        // inner x = 11
    x
result = x           // outer x remains 10
```

The lambda syntax is illustrative; code blocks are **indentation-defined** rather than brace-delimited (see [syntax-and-types.md](spec/syntax-and-types.md#code-blocks-and-data-structures)).

- Visibility is **sequential**: ordinary declarations become visible to later declarations, not earlier ones.
- Functions may be **self-recursive**, as an explicit exception to the ordinary visibility rule.
- A function's references to outer names resolve to the **specific bindings visible at the function's definition**, rather than a later same-name redeclaration or the caller's scope.

```natcode
x = 10
getX = () => x
x = 20
result = getX()       // 10
```

- Local declarations may shadow imported identifiers as well; this is distinct from duplicate *imported* bindings, which are an error.

## Identifier categories

- Ordinary value bindings use Haskell-style **lowercase-leading** names, including Unicode letters supported by Unicode identifier categories, or emoji identifiers.
- Types and constructors use **PascalCase** and cannot use emoji identifiers.
- Namespaces introduced by imports must use **PascalCase**.
- **Top-level values** may *also* use `UPPER_SNAKE_CASE`; this is **allowed but not required**. Types/constructors may not use `UPPER_SNAKE_CASE`. Ordinary local values do not gain this exception.
- A standalone `_` is reserved as a wildcard, not an ordinary binding identifier.
- Unicode emoji sequences are valid value names, including composed emoji such as `👩‍💻`. Which emoji sequences are admitted is LEX-ID-04.

```natcode
maxSize = 100
MAX_SIZE = 100         // allowed at module top level
🚀 = 42
type Point(x: number, y: number)  // illustrative type syntax
```

## Identifier mangling and compilation

Identifiers unsupported by a target language (e.g., emoji) are mapped to generated, target-safe identifiers. Name generation must be **collision-safe**. Source names and internal symbol identities remain available for correct resolution and debugging. The exact output spelling is not part of source-language syntax.

## Exact type inference

- Direct primitive literals infer their exact literal types: `42`, `"Alice"`, `true`, rather than automatically widening to `number`, `string`, `boolean`.
- Compile-time constant expressions infer exact literal results when statically evaluable: `40 + 2` may infer `42`.
- A binding's optional `:` constraint does not erase this precision.
- Precise rules for function return inference and evaluation are recorded in [evaluation.md](spec/evaluation.md); they don't affect basic variable syntax.

## Declaration grammar (schematic)

```ebnf
variableDeclaration = valueIdentifier, [":", typeExpression], "=", expression ;
```

The `valueIdentifier` category depends on scope: top-level `UPPER_SNAKE_CASE` is additionally permitted. The lexical grammar is in [lexical.md](spec/lexical.md); expression and type grammars are PAR-EXPR-01 and PAR-TYPE-01.

# Modules, imports, exports, and program entry

Item status and open questions for this file are tracked in the [parser](scorecards/parser.md), [resolver](scorecards/resolver.md), [types](scorecards/types.md), and [runtime](scorecards/runtime.md) scorecards.

## What is a module?

A module is a **logical, lexically scoped collection of declarations** with its own namespace and an import/export boundary. Its conceptual role is distinct from a package and from a physical file. For Natcode's initial source layout, **each `.nat` source file defines exactly one module**; no explicit module declaration is required.

A source file permits **top-level declarations only** (including imports and the terminal export declaration), not standalone executable expressions. A top-level variable initializer is part of a declaration, not a standalone statement.

Functions associated with types, future extension functions, and constructor-like functions may live in separate file modules and be connected through the import/export and future type-association system. Their syntax and resolution are PAR-EXT-01 and RES-EXT-01.

## Module form

All imports must precede other declarations. Every module must have **exactly one** `export` declaration **at the end** of the module, with nothing declared after it.

```natcode
from "./math" import { PI }

area = PI * 5 * 5

export { area }
```

- `export {}` is required for a library exposing no names.
- A module cannot combine a function entry export with an ordinary object export or have multiple terminal exports.

## Exported kind: object library or function executable

The final export may be an **arbitrary expression**, but its inferred type must statically establish exactly one category:

- **Object** → importable **library module**.
- **Function** → **executable module**, with that function as the program entry point.
- **Primitive or directly exported type** → invalid. Types and primitive values must appear as **properties of an exported object**.
- **Expression potentially returning either object or function** → compilation error; module kind cannot depend on runtime outcomes.

```natcode
PI = 3.14159
square = x => x * x
export { PI, square }        // library: object-shaped public interface
```

```natcode
run = () => print("Hello")
export run                   // executable: function entry
```

```natcode
api = { PI = 3.14159, square = x => x * x }
export api                   // same public interface as export { PI, square }
```

Here `export { ... }` builds the module's exported object. `export api` where `api` is an object exposes its **properties as named exports**, not one implicitly named `api` export. Object literal and function body syntax above is illustrative.

- Both **types and values** can be placed in the same exported object; `export { Point, origin }` is valid.
- A module may **re-export previously imported declarations**, including complete imported namespace values.
- Object properties' **public names must be unique** within the exported interface. Unlike same-scope variable redeclarations, duplicate public export keys are compilation errors.
- **Export aliases** use `=` with the public name on the left: `export { publicName = localName }`.

```natcode
from "./math" import { square }
export { squareNumber = square }
```

## Entry modules

- An executable is selected by **source-file path**, allowing multiple executable files in the same project; command shape `natcode run src/main.nat` is illustrative.
- An executable module is **not importable** by other modules.
- Its entry function can be **imported from a library module**; it need not be declared locally.
- Each module has only one terminal export, so an executable module has one entry function.
- The **entry function's parameter shape, effect/purity model, and runtime context** are RUN-ENTRY-01. There is no mandated `main` name.

```natcode
// app.nat
run = () => print("Hello")
export { run }               // library

// main.nat (different file)
from "./app" import { run }
export run                   // executable
```

## Import syntax and ordering

Natcode uses **file-first syntax**:

```natcode
from "./math" import Math
from "./math" import { PI, square }
from "./math" import *
from "./math" import { PI }, Math
```

- `Math` is a **PascalCase namespace alias**.
- `{ PI, square }` imports named exports as direct local bindings.
- `*` imports **all possible exported names** as direct local bindings; `_` is **not** an import wildcard.
- The combined form `{ PI }, Math` imports `PI` directly and places only the **remaining** names in `Math`; `Math.PI` is absent from that combined import.
- The designer also wants remaining exports to be importable unqualified via wildcard in a combined selective import; the grammar for this is PAR-IMP-08.
- Import aliases use `=` with local alias on the left: `from "./math" import { localName = publicName }`.
- Bare `from "./math"` without `import ...` is **invalid**.
- Multiple import declarations from the **same module are allowed** and resolved independently. For example, separate `{ PI }` and `Math` imports leave `PI` inside `Math`; one combined `{ PI }, Math` import removes `PI` from that `Math` view.

## Paths and dependencies

- Ordinary import paths must be **static string literals**, not computed expressions or runtime variables.
- Local imports use explicit relative prefixes `./` or `../`, resolved against the importing file.
- `.nat` can be omitted for Natcode source modules; non-Natcode formats (such as `.json`) use an explicit extension.
- Direct imports of **JSON** are supported in principle; their value representation is RES-MOD-08. Other non-Natcode file types are RES-MOD-09.
- Built-in and external package path schemes are RES-MOD-07.
- **Circular module dependencies are forbidden**, including cycles through several modules; the compiler reports an error.

## Import names and shadowing

- Two imports that introduce the **same local identifier** are a **compilation error**, even if imported from the same module, even if they identify the exact same source binding, and even if unused.
- Different aliases or namespaces may be used to disambiguate.
- This is not inconsistent with ordinary binding redeclaration: a later **local declaration can shadow an imported binding** according to Natcode's immutable sequential scope rules.

```natcode
from "./math" import { MATH_PI = PI }
from "./geometry" import { GEO_PI = PI }

PI = 3.14    // allowed local declaration
```

## First-class namespaces and persistent updates

Namespace imports are **first-class immutable values**, not compile-time-only symbols. They can be assigned, passed to functions, returned, and nested in other objects and namespaces.

Multiple imports of the same module initially reference the **same logical exported namespace value**. An update such as `Math.PI = 3.14` constructs a **new immutable namespace value** for the current binding rather than mutating the shared original. Other references and previously captured values retain the older version. Persistent data structures and structural sharing are intended implementation techniques; detailed dotted-update syntax and semantics are PAR-UPD-01 and RUN-UPD-02.

## Exported object shapes and optional properties

- The exported object may have multiple possible statically inferred shapes (e.g., a union of object types).
- The compiler must statically enumerate the **finite set of possible public property names**, but the presence and values of each property can vary at runtime.
- A named import is legal when the property exists in **at least one** possible export shape. If absent in some branches, its inferred type includes a `None` case.
- Importing a property that exists in **no** possible export shape is a compile-time error.
- Wildcard imports include the **union of all possible export names**, even conditionally present ones.
- No `null` or `undefined` values are intended for Natcode. The exact semantics and spelling of `None` are TYP-NONE-01.
- A dynamic object with arbitrary runtime keys may be exported **inside a statically named property** (e.g. `export { data }`); arbitrary unenumerable runtime keys are not allowed as the module's top-level public export interface.

```natcode
// api.nat (illustrative conditional syntax)
export if condition then
    { x = 10, y = 20 }
else
    { x = 30, z = 40 }
```

```natcode
// consumer.nat
from "./api" import *
// x: 10 | 30
// y: 20 | None
// z: 40 | None
export {}
```

## Lazy module evaluation

- Importing a module does not eagerly evaluate all its top-level values.
- Bindings are evaluated on first demand and **memoized** (call-by-need).
- Exported object properties are independently lazy; accessing one property does not evaluate another unrelated property.
- Arbitrary factory expressions can produce exported objects, and deferred function bodies may expose lazily computed members. Lowering this through arbitrary function calls, and the purity/effect boundary, are RUN-LAZY-05.

```natcode
export { cheap = 42, expensive = expensiveCalculation() }
// Accessing cheap does not force expensiveCalculation().
```

# Type inference, lazy evaluation, and debugging

Item status and open questions for this file are tracked in the [types](scorecards/types.md), [runtime](scorecards/runtime.md), and [debugger](scorecards/debugger.md) scorecards.

## Literal precision

- Literal expressions have exact literal types by default.
- Pure constant operations may propagate exact results: `40 + 2` can infer `42`.
- Type constraints (`:`) check assignability without widening.

## Function return inference: context-independent

The designer revised an earlier broader constant-evaluation proposal: **function return types are inferred from parameter types and the function's own body**, not specialized using the specific values passed at each call site, nor values outside the function. Exact types can propagate through function-local variables.

```natcode
// Illustration of intended syntax and inference:
test(x: number) => x * 2   // return: number
test(x: 24) => x * 2       // return: 48
```

The function syntax in these examples is illustrative (PAR-FN-01, TYP-FN-03); they illustrate type inference rules only.

Compile-time evaluation rules should be standardized and deterministic. When an attempt to evaluate a pure expression exceeds its budget, **fall back to ordinary sound static inference rather than failing solely due to the budget**. Exact budgets and the relationship to type checking are TYP-EVAL-02.

## Laziness

- Top-level module bindings and exported object members are call-by-need and cached after evaluation.
- Unused work should not execute, regardless of whether the enclosing object originates in an expression or factory function, subject to actual data dependencies.
- Persistent immutable data structures allow versions to share storage; memoization avoids repeated computation. These are complementary, not synonymous.

## Debugging

Debug builds **preserve the language's lazy semantics**. Debugging tools may show suspended computations and let the developer explicitly force/step into them. Automatically evaluating every function in debug mode is rejected, because it changes program behavior. Production builds may remove unused pure computations and debug builds may retain richer source metadata.

The debugger interface, effects, resource limits, and force semantics are DBG-API-01.
