# Lexical structure (core subset)

Item status and open questions for this file are tracked in the [lexer scorecard](scorecards/lexer.md).

Source text is UTF-8. Positions are reported as byte-offset spans plus 1-based line and column, where columns count Unicode scalar values.

## Tokens

| Category | Forms |
| --- | --- |
| Reserved keywords | `from`, `import`, `export`, `unique`, `type`, `fn`, `when`, `where`. These are case-sensitive, hard-reserved words (LEX-KW-01, LEX-KW-04 through LEX-KW-07, LEX-KW-12, LEX-KW-13). |
| Boolean literals | `true`, `false` |
| Identifiers | Unicode identifiers per UAX #31: first character is `XID_Start` or `_`; following characters are `XID_Continue`. Letters of any script (`café`, `größe`, `π`, `中文`) are allowed. |
| Wildcard | A standalone `_` is its own token, never an identifier. `_x`, `__`, and `x_` are identifiers. |
| Numbers | Decimal integers (`42`) and decimal fractions (`3.14159`), using ASCII digits only. |
| Strings | Double-quoted, single-line: `"Alice"`, `"./math"`. Any character except a line break is allowed, including non-ASCII. |
| Operators and punctuation | `=` `=>` `:` `\|` `&` `/` `as?` `{` `}` `(` `)` `,` `.` `*` `+` `-` `!` `<` `<=` `>` `>=` `==` `!=` `&&` `||` |
| Comments | `// …` to end of line; `/* … */` block comments, which nest. Comment text produces no ordinary tokens. Physical line breaks inside block comments must remain visible to layout analysis (LEX-COM-04), whether through newline tokens or source-position/layout metadata. |
| Line breaks | LF or CRLF; each is one newline token. Spaces are insignificant between tokens. |

The reserved words are recognized as keywords regardless of position; they cannot name ordinary bindings. `unique` is the hard-reserved modifier in nominal declarations written `unique type`. `alias` is an ordinary identifier, not a declaration keyword. Keyword spellings are permitted as object property names, with details of the object grammar still to be determined (PAR-OBJ-01). `match`, `if`, `else`, `elif`, and `case` are not reserved words or language control-flow constructs. The unified matching and conditional keyword is `when` (LEX-KW-07). `return` is not a control-flow construct or keyword. `try`, `catch`, and `throw` are not reserved or built-in exception constructs (LEX-KW-11). `null` is not a native literal or reserved word; absence is represented using constructors such as `None`. `where` is the refinement-type keyword. `as?` is one indivisible runtime-validation operator token (LEX-OP-05); `as` by itself remains an ordinary identifier, and whitespace-separated `as ?` is not the operator. Value-expression operators `-`, `!`, `<`, `<=`, `>`, `>=`, `==`, `!=`, `&&`, and `||` are approved by LEX-OP-03; multi-character operators use maximal munch (LEX-OP-02). A future pipe operator remains open under PAR-PIPE-01. Further words, including `then` and generator/effect vocabulary, remain open questions (LEX-KW-03).

## Layout and indentation

Source indentation has **no fixed required width**. Explicit executable blocks are delimited by braces. Leading whitespace remains available for parsing `when` and `where` branch lists and nominal constructor lists, even when those constructs occur inside `{}` or `()`. These lists use their grammar and applicable branch constraints to establish membership: differing indentation alone is not a compile error when ownership is unambiguous. Blank lines and comment-only lines do not change grouping. An unresolved ambiguous grouping is a compilation error; the compiler must not guess or automatically reindent it.

Natcode has **no explicit line-continuation marker**, including backslash continuation. Parentheses and other expression delimiters may allow multiline expressions; their complete newline grammar is still to be specified (PAR-BLK-02, PAR-EXPR-01). Canonical formatting uses four spaces and is part of the Natcode toolchain (TOOL-FMT-01). Tabs and other whitespace categories remain separately open in LEX-WS-02. Under LEX-COM-04, block comments preserve physical line boundaries for layout: removing comment text never joins two physical lines into one logical line. Comment-only lines remain layout-neutral, and following code retains the layout of its own physical line. The representation of these boundaries as newline tokens or source-position/layout metadata is an implementation choice.

## Identifier normalization

Identifiers are normalized to Unicode **NFC**, so visually identical spellings (precomposed `é` versus `e` followed by a combining acute accent) name the same identifier. String literal contents are **not** normalized.

## Number rules

- A digit separator `_` may appear only **between two digits**: `1_000` and `3.141_59` are valid; `1__0`, `1_`, `1_.5`, `1._5`, and `1.5_` are errors.
- A fraction requires a digit (or a misplaced `_`) immediately after the `.`. Otherwise the number ends before the `.`: `1.` is the number `1` followed by `.`, and `1.foo` is `1`, `.`, `foo`.
- A number cannot begin with `.`: `.5` is `.` followed by `5`.
- A leading `-` is not part of a number literal; it is the separate `-` operator token (LEX-OP-03), so `-1` is `-` followed by `1`.
- A number may not be directly followed by identifier characters. `42abc`, `1_a`, and `3.14x` are each a single error, as are `1e10` and `0x1F` (see LEX-NUM-05 and LEX-NUM-06).

## Strings

- Escape sequences are **not supported**. A backslash anywhere inside a string literal is an error, and it does not escape a following `"`.
- A string that reaches a line break or the end of input before its closing `"` is an error.

## Lexical errors

Any character that cannot begin a token is an error, including emoji, non-identifier symbols such as `∑` or `€`, and ASCII characters outside the operator set (for example `;`, `@`, `?`). An unterminated block comment is an error. Lexing recovers after every error and reports all diagnostics in source order.

# Broader syntax and type-system decisions

Item status and open questions for this file are tracked in the [parser](scorecards/parser.md), [types](scorecards/types.md), and [tooling](scorecards/tooling.md) scorecards.

## Code blocks and data structures

- **Arbitrary executable scopes use braces `{}`**, including named function bodies and multi-expression arrow and `when` branch bodies (PAR-BLK-01). Indentation alone does not create an executable scope.
- A single-expression arrow or `when` branch body can omit braces. Braced blocks yield their final expression; no explicit `return` is required or supported (PAR-FN-03).
- **Algebraic constructor lists and `when`/`where` branch lists** retain newline-based, layout-sensitive presentation. Exact indentation width is not a syntax requirement: the parser recovers unambiguous ownership from grammar and applicable constraints, and rejects unresolved ambiguity rather than guessing (LEX-IND-01, PAR-LAYOUT-01). These lists can occur inside braces and parentheses.
- Blank and comment-only lines never change ownership. Explicit backslash line continuation is not supported. The full statement/newline grammar and malformed-layout error recovery remain PAR-BLK-02 and LEX-IND-02.

The following body form is approved; complete named-function parameter grammar remains PAR-FN-01:

```natcode
fn calculate(x) {
    doubled = x * 2
    doubled + 10
}
```

An arrow or `when` branch may return a single expression directly, including a nested `when`; a multi-expression body uses `{}`:

```natcode
result = when input
    Option.Some(value) => value + 1
    Option.None => {
        fallback = 0
        fallback
    }
```

Objects also use braces, but **object literal properties use `:`**, while ordinary value declarations use `=`. Immediately after `=>`, unparenthesized `{}` means an executable block, so direct anonymous-object results must be parenthesized (PAR-OBJ-02):

```natcode
user = { name: "Ada" }
getUser = () => ({ name: "Ada" })
getName = () => {
    name = "Ada"
    name
}
```

Object literals may be empty. Non-empty entries are comma-separated even when written on separate lines, and a trailing comma is optional. Static keys may be identifiers, string literals, or numeric literals. Identifier shorthand is supported, so `{ name }` means `{ name: name }`. Computed keys use `[expression]: value`:

```natcode
key = getKey()

user = {
    name: "Ada",
    "display-name": "Ada",
    123: "numeric key",
    [key]: 36,
}
```

Repeating the same written static key in one object literal is a compile error. The type representation of dynamic computed keys, including possible collisions with statically known properties and the relationship between objects and `Map`, remains TYP-OBJ-01. Object spread syntax is tracked separately by PAR-OBJ-03.

Exported-object forms such as `export { value }` and export aliases with `=` are separate grammar, unaffected by the object-literal property rule.

## Canonical formatting

Natcode has an **opinionated built-in formatter** (`natcode fmt`) and a non-mutating check mode (`natcode fmt --check`) without a separate lint or Prettier dependency (TOOL-FMT-01). The compiler accepts flexible indentation widths for recoverable structures, and the formatter produces **four spaces per level** as the canonical presentation. Compilation does not reformat files.

The formatter uses parsed structure and never changes block or branch ownership. It preserves explicitly written executable braces, including braces around a single expression, and expands single-line braced executable bodies onto separate lines rather than removing their braces:

```natcode
// Written
Result.Success(value) => { value + 1 }

// Canonical
Result.Success(value) => {
    value + 1
}
```

When syntax unambiguously determines constructor or branch membership, the formatter corrects alignment. If multiple interpretations remain and the compiler cannot safely determine ownership, it reports a compilation error with actionable diagnostics; it does not apply a speculative fix. Full proof of indentation safety and remaining error-recovery details are tracked separately (PAR-LAYOUT-01, LEX-IND-02).

## Value expression grammar and precedence

Natcode uses parenthesized function calls only: `f(x)`, `f()`, and chained forms such as `foo.bar(x).baz()` are valid. Whitespace application such as `f x` is invalid.

Ordinary value-expression operators bind from highest to lowest as follows:

| Precedence | Form | Associativity |
| --- | --- | --- |
| 1 | member access `.`, call `()` | postfix, chained left-to-right |
| 2 | unary `!`, unary `-` | prefix |
| 3 | `*` | left |
| 4 | `+` | left |
| 5 | `<`, `<=`, `>`, `>=`, `==`, `!=` | non-associative |
| 6 | `&&` | left, short-circuiting |
| 7 | `||` | left, short-circuiting |
| 8 | `=>` | right |

Thus `a + b * c` means `a + (b * c)`, `!ready && enabled` means `(!ready) && enabled`, and `x => y => x + y` means `x => (y => x + y)`. Comparison operators do not chain: `a < b < c` is invalid; write `a < b && b < c`.

Member access and calls form one postfix layer, so `foo.bar(x).baz()` groups as `(((foo.bar)(x)).baz)()`. Type-expression `|` and `&` are separate union/intersection operators and are not ordinary value operators. Pipe syntax and precedence remain open under PAR-PIPE-01. The dedicated runtime-validation form `as?` keeps the grammar defined by PAR-VAL-01 rather than becoming a general binary value operator.

## When expressions

Natcode uses one `when` keyword for both structural pattern matching and conditional branching (PAR-COND-02). It does not have separate `if`/`else` or `case` control-flow constructs.

- **Subjectful** `when expression` selects a branch by matching patterns against that subject.
- **Subjectless** `when` evaluates Boolean branch conditions in source order and selects the first true condition.
- Both forms are expressions that produce the selected branch's value.

The fat arrow `=>` is the approved separator between a branch pattern or condition and its result (PAR-COND-04). Each branch may produce a single expression without braces, including another `when`; branches with multiple declarations or expressions use `{}` and yield the final expression. Explicit braces around a single expression remain valid (PAR-BLK-01). The full pattern and guard grammar remains open (PAR-COND-01, PAR-PAT-01):

```natcode
result = when option
    Some(value) => value
    None => 0

size = when
    x > 10 => "large"
    x > 5 => "medium"
    _ => "small"
```

Subject-based branches may mix literals, nominal constructor patterns, and references to user-defined unary Boolean predicate functions. A predicate function receives the subject as its argument; subjectless branches evaluate Boolean expressions as written. Branches are processed in source order.

Both forms must be exhaustive (TYP-PAT-01). The remaining possible value set must be provably `Empty` after the branches, otherwise a final `_` is required. `_` stands for the remaining universal case, may occur **at most once**, and must be **last**. A provably redundant `_` or any other provably unreachable `when` branch is a **compilation error**, not a warning. Restricted input types participate in this calculation, so constructors already eliminated from the subject type do not need branches. Arbitrary predicates do not establish exhaustiveness unless their coverage can be proven. In ambiguous layout, diagnostics should explain why plausible branch ownership interpretations fail; no layout fix is applied by guessing. Pattern guards and the complete compound-pattern grammar remain open.

## Declaration keywords and expression results

- `fn` introduces named function declarations (PAR-FN-02). Parameter and body syntax remain open (PAR-FN-01).
- Functions return the value of their final expression; there is no `return` statement or explicit early return (PAR-FN-03).
- `unique type` introduces a fresh **nominal** type identity (PAR-TYPE-03, TYP-NOM-01), even when its constructor payload types match another type.
- `type Name = expression` names an existing type expression or constructor symbol transparently, without creating a new nominal identity (PAR-TYPE-05, TYP-ALI-01, TYP-ALI-02). Constructor-symbol names retain construction and pattern behavior. The full expression grammar remains PAR-TYPE-01.
- `unique type Name(...)` and `unique type Name` with constructor branches introduce nominal constructors (PAR-TYPE-04, PAR-TYPE-06). Bare `type Name(...)` and `unique type Name = expression` are invalid. Further declaration and generic grammar remains open (PAR-TYPE-02).
- Ordinary variable bindings continue to use keyword-free `name = expression` declarations (PAR-DECL-01).

## Inference-first philosophy

Natcode seeks a TypeScript-like ergonomics with a substantially more functional model, emphasizing purity, piping, and pattern matching. These are **design goals** (see RUN-EFF-01, PAR-PIPE-01, and PAR-PAT-01).

Ordinary variable types and function return types are intended to be inferred. The optional declaration constraint `x: Type = expression` is permitted as an **assignability check** without replacing or widening the inferred type; this updates the earlier inference-only proposal.

## Nominal types, constructors, and aliases

A `unique type` declaration creates a fresh nominal identity. Constructing values of two independently declared nominal types does not make those values interchangeable, even when their payload types coincide (TYP-NOM-01).

```natcode
unique type UserId(number)
unique type ProductId(number)

userId = UserId(123)
productId = ProductId(123)
```

Nominal wrappers do **not** implicitly convert to their payload types or automatically inherit their operators (TYP-NOM-02). User-defined operator syntax and resolution remain open until function semantics are designed.

A constructor can have multiple positional parameters. The constructor form is also a pattern that binds the contents of its fields; there is no automatically generated `.value` accessor (TYP-NOM-03, TYP-NOM-04, PAR-PAT-01).

```natcode
unique type Point(number, number)

point = Point(10, 20)
coordinates = when point
    Point(x, y) => { x, y }
```

The `when` branch and record literal syntax in these examples is illustrative; the pattern-matching ability to destructure constructors is approved, while the complete grammar is PAR-PAT-01 and PAR-COND-01.

An algebraic nominal type may declare multiple constructors in a constructor list; its indentation is normalized by the formatter and does not independently establish semantic nesting. A constructor is qualified by its declaring type by default; the constructor's unqualified name is **not** automatically in scope (TYP-ADT-01, PAR-TYPE-06, RES-NAME-06).

```natcode
unique type Option
    Some(Any)
    None

present = Option.Some(42)
absent = Option.None
```

A transparent `type Name = ...` declaration can name a type expression or an existing constructor symbol. Constructor aliases preserve the original constructor identity and are usable in value construction and constructor patterns (TYP-ALI-01, TYP-ALI-02).

```natcode
type Some = Option.Some

value = Some(42)
unwrapped = when value
    Some(x) => x
```

In **type-expression context**, applying an existing nominal constructor to type arguments describes a subset of that nominal type constrained by its payload values; in **value-expression context**, applying it constructs a value (TYP-NOM-05). Omitting the arguments names the entire nominal type with no further restriction.

```natcode
unique type Value(string)
unique type Value2(number)

type Z = Value("one" | "two") | Value2(1 | 2)
type Unrestricted = Value | Value2
```

For a single-payload constructor, `Value(A | B)` represents the same set of possible values as `Value(A) | Value(B)`. For multiple arguments, correlations must be preserved: `Point(1 | 2, 3 | 4)` represents four combinations, while `Point(1, 3) | Point(2, 4)` represents only two. The complete grammar for literal type expressions is PAR-TYPE-01.

Nominal types may contain other nominal types through ordinary constructor parameters (TYP-NOM-06).

```natcode
unique type Position(number, number)
unique type Color(string)

unique type Sprint(Position, Color)
// Equivalent unrestricted parameter types:
// unique type Sprint(Position(number, number), Color(string))

sprint = Sprint(Position(10, 20), Color("red"))
```

These nested values are constructor arguments; this declaration **does not imply** implicit projection, inheritance, an interface, independent-aspect composition, or automatic reconstruction after a nested value is transformed. No separate nominal-combination operator or construct is approved. The previously explored special combination syntax is rejected in favor of ordinary nesting. How a function might preserve a containing value while transforming a nested value, versus return an unrelated value, remains an open question (TYP-FN-05).

## Refinement types with `where`

`where` is a postfix type operator that describes a **subset** of the type expression on its left (TYP-REF-01, PAR-REF-01). It does not create a nominal identity. A branch predicate is Boolean: values for which the predicate is true remain in the type, and values for which it is false are excluded.

```natcode
type Positive = number where
    x => x > 0

type AboveDiagonal = Position where
    (x, y) => x > y
```

A restricted alias remains assignable to the type it restricts. The reverse assignment is accepted only when the compiler can establish that the value satisfies the restriction (TYP-REF-11).

### Where patterns and filtering

`where` and subjectful `when` use the same pattern language (PAR-PAT-02). Literal patterns, constructor patterns, wildcards, and constructor destructuring therefore mean the same thing in both constructs. Unlike `when`, however, `where` is a filter and **does not require exhaustive branches** (TYP-REF-03). Its branch list is indentation-insensitive when branch ownership is unambiguous; ambiguous ownership is a compile error rather than a guessed autofix (PAR-LAYOUT-01).

A pattern claims the part of the input type that it matches. Its Boolean result decides which values from that matched part remain. A value whose pattern matched but whose predicate is false is excluded; it does not fall through to a later branch. Values not matched by any branch are also excluded.

```natcode
unique type Option
    Some(number)
    None

type PositiveOption = Option where
    Some(x) => x > 0
```

Here positive `Some` values remain, negative and zero `Some` values are excluded, and `None` is excluded because no branch includes it.

Ordinary branch patterns must describe disjoint regions. If two ordinary branches could match the same value, that is a compile error. `_` is special: it denotes only the region not matched by earlier branches. Consequently it must be final whenever it consumes the entire remaining region, and any branch after the remaining region is already `Empty` is a compile error.

```natcode
type KeepOtherCases = Option where
    Some(x) => x > 0
    _ => true
```

In this example, `Some(-1)` is still excluded: it matched `Some(x)` and failed that predicate, so it does not reach `_`. The wildcard includes only values from constructors or regions that earlier patterns did not match.

Explicit `true` and `false` branches are valid. A bare constructor is sugar for including that entire constructor:

```natcode
unique type Result
    Success(number)
    Failure(string)

type Successful = Result where
    Success

// Equivalent ways to include every Success value:
type Successful2 = Result where
    Success => true

type Successful3 = Result where
    Success(_) => true
```

For a nullary constructor, `None` and `None => true` are likewise equivalent. Explicit exclusions such as `Failure => false` and catch-alls such as `_ => false` remain valid even when omission would currently produce the same set.

A restriction that removes every possible value resolves to `Empty` and is valid. `Empty where ...` also resolves to `Empty` (TYP-REF-07).

### Binding and destructuring the input

A single binder may bind the entire candidate value regardless of how many constructors the input type contains:

```natcode
(Foo | Bar) where
    value => isAllowed(value)
```

Positional destructuring without a constructor name is available only when the complete type on the left has one unambiguous constructor shape (PAR-REF-02). One exposed parameter may omit parentheses; two or more require parentheses.

```natcode
type Positive = number where
    x => x > 0

type AboveDiagonal = Position where
    (x, y) => x > y
```

If different nominal constructors are possible, positional destructuring cannot choose between them:

```natcode
// Invalid: Foo and Bar are different nominal constructors.
(Foo | Bar) where
    (x, y) => x > y

// Valid: each branch says which constructor it handles.
(Foo | Bar) where
    Foo(x, y) => x > y
    Bar(x, y) => x < y
```

Within `Option where ...`, unqualified constructor names such as `Some` and `None` resolve contextually to `Option.Some` and `Option.None` without becoming bindings in the surrounding scope (RES-REF-01). Fully qualified names remain valid. If the input type contains multiple possible constructors with the same short name, that short name is ambiguous and must be qualified.

### Where placement and precedence

`where` is a normal type operator and may appear wherever a type expression is already permitted (PAR-REF-01). The `where` keyword must start on the **same physical line** as the type or constructor it restricts (for a parenthesized expression, the line of its closing `)`); moving it to the next line is invalid. Its branch indentation can be normalized when ownership is unambiguous (LEX-IND-01). It binds more tightly than the set operators `|`, `&`, and `/`:

```natcode
A | B where x => predicate(x)
// means:
A | (B where x => predicate(x))
```

Parentheses select a larger input explicitly:

```natcode
(A | B) where
    A(x) => ...
    B(x) => ...
```

Directly chaining `where` operators is rejected. Combine conditions in one restriction or name the intermediate type instead:

```natcode
// Invalid:
number where x => x > 0 where x => x < 10

// Valid:
type Positive = number where
    x => x > 0

type SmallPositive = Positive where
    x => x < 10
```

A `where` may not be written directly after an already-applied constructor type such as `Position(0, number)` or `Position(number, number)` (PAR-REF-03). Restrict an individual parameter inside the constructor application, or name the specialized type and refine that name:

```natcode
type PositiveXAxis = Position(
    0,
    number where y => y > 0
)

type XAxis = Position(0, number)
type PositiveXAxis2 = XAxis where
    y => y > 0
```

The second form sees the constructor shape exposed by `XAxis`: only its one remaining parameter. A specialized type with zero exposed parameters, such as `Position(0, 0)`, has nothing for `where` to bind and cannot be refined again with `where`. `Empty` is the explicit exception described above.

A qualified constructor symbol may be refined directly:

```natcode
type PositiveSome = Option.Some where
    x => x > 0
```

### Restrictions in nominal declarations

Restrictions in a nominal declaration may be attached to individual constructor parameters or to the whole single constructor (TYP-REF-02):

```natcode
unique type Response
    Success(number where code => code >= 200 && code < 300)
    Failure(string)
```

The inner `where` can reference only that single parameter. It cannot reference adjacent constructor parameters.

A restriction may instead apply to a constructor as a whole, allowing relationships between that constructor's parameters:

```natcode
unique type Range(number, number) where
    (start, end) => start < end
```

For algebraic types, individual constructors may have whole-constructor restrictions:

```natcode
unique type Response
    Success(number) where
        code => code >= 200 && code < 300
    Failure(string) where
        message => message != ""
```

A declaration-wide `where` on a nominal type with multiple constructors is **not supported**:

```natcode
// Invalid: a declaration-wide `where` cannot follow a multi-constructor type.
unique type Response
    Success(number)
    Failure(string)
where
    Success(code) => code >= 200 && code < 300
    Failure(message) => message != ""
```

To filter an existing algebraic nominal type as a whole, use a transparent `type` declaration instead:

```natcode
type FilteredResponse = Response where
    Success(code) => code >= 200 && code < 300
    Failure(message) => message != ""
```

`where` on a constructor declaration remains legal and can relate multiple parameters, unlike a parameter-local restriction. These restrictions do not change nominal identity. For example, restricting the payload accepted by a nominal `Port` constructor does not make `Port` assignable to `number`.

When more than one restriction applies, all of them must hold; their effect is intersection (TYP-REF-02).

### Specialized aliases and constructors

Applying a constructor in a type expression fixes any literal positions and leaves the remaining positions as the parameters exposed by the resulting specialized type (TYP-NOM-07):

```natcode
unique type Position(number, number)

type XAxis = Position(number, 0)
type Center = Position(0, 0)

x = XAxis(10)    // constructs Position(10, 0)
center = Center  // zero-parameter application
center2 = Center()
```

A zero-parameter application may omit `()` in both type and value contexts (TYP-NOM-08). Thus `x: Center` and `x: Center()` name the same type, and nullary constructors such as `Option.None` and `Option.None()` are equivalent.

A restricted alias preserves the constructor structure of what it restricts rather than inventing new constructor shortcuts (TYP-REF-04). For an algebraic type, every constructor whose restricted set is not proven `Empty` is exposed under the alias namespace:

```natcode
unique type Option
    Some(number)
    None

type PositiveOption = Option where
    Some(x) => x > 0

value = PositiveOption.Some(5)
```

`PositiveOption.None` is absent because `None` was eliminated. `PositiveOption(5)` is not introduced, because `Option` itself was never a constructor. If the developer wants a directly callable constructor alias, the constructor itself can be restricted:

```natcode
type PositiveSome = Option.Some(number where x => x > 0)
value = PositiveSome(5)
```

A constructor is removed from a restricted alias only when the compiler can prove that its remaining set is `Empty`. Lack of proof that a constructor is inhabited is not itself proof that the constructor is empty; construction still must establish the restriction for the specific value.

Construction through a restricted alias enforces every applicable restriction.

### Constructibility through set algebra

Constructibility is determined from the **normalized resulting type**, not mechanically inherited from one operand (TYP-REF-05).

If a union or intersection still exposes one common effective constructor shape, the resulting alias remains directly constructible:

```natcode
unique type Vector3(number, number, number)

type PositiveX = Vector3 where
    (x, y, z) => x > 0

type PositiveY = Vector3 where
    (x, y, z) => y > 0

type EitherPositive = PositiveX | PositiveY
type BothPositive = PositiveX & PositiveY
```

Both aliases still expose the same three `Vector3` parameter positions, with their combined restrictions.

Sharing only the same nominal origin is not enough:

```natcode
type XAxis = Position(number, 0)
type YAxis = Position(0, number)

type Axis = XAxis | YAxis
```

`Axis` is a valid type but is not directly callable: `XAxis` and `YAxis` expose different parameter positions. By contrast:

```natcode
type Center = XAxis & YAxis
```

normalizes to `Position(0, 0)`, so `Center` has the resulting zero-parameter constructor.

Set difference preserves constructibility when its normalized result still has one effective constructor shape. The type-expression operator `A / B` denotes values in `A` that are not in `B` (TYP-UNI-10).

### Purity and lexical capture

A `where` predicate must be pure and deterministic (TYP-REF-06). Type membership cannot depend on I/O, mutable state, time, randomness, network or database state, or other effects.

A predicate may call eligible pure functions. It may also close over earlier immutable bindings in lexical scope (RES-REF-02):

```natcode
minimum = 10

type AboveMinimum = number where
    x => x > minimum
```

The captured binding is the specific earlier binding, consistent with Natcode's lexical binding model. Values needed for mandatory compile-time validation must still be evaluable or provable by the compiler; effectful or runtime-dependent state is not permitted in a type restriction.

Restricted constructors are not themselves Boolean membership tests. Compose restrictions through types instead:

```natcode
type Positive = number where
    x => x > 0

type SmallerPositive = Positive where
    x => x < 10
```

### Runtime validation

The infix operator `as?` explicitly validates membership in a restricted type at runtime (TYP-REF-12, PAR-VAL-01). It is validation, not conversion or construction: on success the result is the original value, now known as the requested target type; on failure the result is a designated `ValidationError` value.

Every runtime-validatable restricted target `T` has a **validation input type** `U`: the compatible unrestricted type whose values can safely be checked by `T`'s restrictions. For example, the validation input type of `number where x => x > 0` is `number`, and the validation input type of `Value("one" | "two")` is `Value`. A source expression in `x as? T` must already be statically assignable to `U`; `as?` does not perform dynamic discrimination between unrelated underlying types. Use `when` for that. A target whose validation input type is `Empty` is invalid for `as?`, because no value can be supplied to such a validator.

```natcode
type Positive = number where
    x => x > 0

n: number = getNumber()
validated = n as? Positive       // Positive | ValidationError

text: string = getString()
invalid = text as? Positive      // compile error: string is not a number
```

The right operand of `as?` is a complete type expression. Thus:

```natcode
x as? number where n => n > 0
```

means:

```natcode
x as? (number where n => n > 0)
```

For every valid application, the result type is stably `T | ValidationError` (TYP-REF-13). This signature does not collapse merely because the compiler can prove that the particular validation will succeed or fail. A proof may remove runtime work or precompute the result, but it does not change the expression's type. Whether such statically decided validations should produce a diagnostic remains open (TYP-DIAG-03).

Runtime validation applies to any runtime-checkable restricted subset with one compatible non-empty validation input type, not only a subset written directly with `where` (TYP-REF-14). This includes constructor-payload restrictions and compatible unions, intersections, and differences. Sibling refinements of the same validation input type may validate against one another. A refinement built on another refinement validates the full inherited restriction chain.

For a union target, validation succeeds when any alternative succeeds. Failures from alternatives are discarded when the union succeeds; if every alternative fails, the resulting `ValidationError` captures the failures from all determinable alternatives. For an intersection target, every component must succeed and all determinable component failures are collected. Set-difference validation follows ordinary membership semantics: the value must belong to the left side and not the right side (TYP-REF-14, TYP-REF-15).

`ValidationError` is a first-class designated error type that carries the type-level validation failures encountered while checking the requested target. Validation evaluates all applicable checks needed to collect every determinable failure rather than stopping after the first independent failure (TYP-REF-15). The exact structure of `ValidationError`, developer-defined type-level validation messages or metadata, and their representation remain open (TYP-REF-16).

A target type therefore conceptually induces a validator with the shape `U -> T | ValidationError`. General expression-placeholder syntax such as `_ as? T`, including multiple-placeholder and scope rules, remains open (PAR-EXPR-02). Pipe syntax and any error-aware short-circuiting behavior also remain open (PAR-PIPE-01, TYP-REF-17).

## Union and intersection types

- `|` is mathematical **set union**: a value belongs to `A | B` precisely when it belongs to `A` or `B`. Neither union nor intersection creates a new nominal identity (TYP-UNI-06).
- Simplification/consolidation of a union is permitted **only when it preserves the exact represented set of possibilities**. In particular, preserve correlations between fields and exclusions; do not merge distinct object variants in ways that admit combinations not present in the original union.
- `&` is mathematical **set intersection**: a value belongs to `A & B` precisely when it belongs to **both** types. It never constructs or combines constituent values and is distinct from `:` constraints (TYP-UNI-06).
- `/` is mathematical **set difference** in type expressions: `A / B` contains exactly the values in `A` that are not in `B` (TYP-UNI-10).
- `Any` is the universal type (`T | Any = Any`, `T & Any = T`). `Empty` denotes the empty type: no values inhabit it. Thus `A | Empty = A` and `A & Empty = Empty` (TYP-UNI-07).
- An intersection proven empty resolves to `Empty` and is **valid**, whether direct, nested, or involving explicit `Empty`. The declaration itself causes no warning or error merely for being empty. Attempting to provide a value where the type is uninhabited is an error (TYP-UNI-08).
- Independently declared, unrelated nominal constructor types are disjoint: for example, `UserId & ProductId` is `Empty` (TYP-UNI-09). Nominal subtyping or other explicit overlapping-identity relationships are not introduced by ordinary constructors.

For example, this union:

```natcode
{ kind: "left", value: number }
|
{ kind: "right", value: string }
```

must not be simplified into:

```natcode
{ kind: "left" | "right", value: number | string }
```

because the latter would allow a `"left"` tag paired with a `string` value, which the original type excludes. The record-type syntax here is illustrative.

Set identities include `A | B = B | A`, `A | A = A`, `A & B = B & A`, and `A & A = A`. More detailed structural membership and normalization choices remain TYP-UNI-04. Set difference `/` is approved in TYP-UNI-10; a standalone complement operator remains TYP-UNI-05. Generic types remain TYP-GEN-01; broader subtyping remains TYP-CON-03.

## Target directions

Natcode is intended to support a native interpreter and compilation to JavaScript, WebAssembly, C, and potentially Python (PY-TGT-01). These are project goals rather than language semantics. A shared compiler IR/runtime design and the implementation language are TOOL-ARCH-01.

# Variable declarations and identifiers

Item status and open questions for this file are tracked in the [parser](scorecards/parser.md), [resolver](scorecards/resolver.md), and [types](scorecards/types.md) scorecards.

## Declaration syntax

```natcode
identifier = expression
identifier: Type = expression
```

- No `val`, `let`, or `var` declaration keyword is required.
- Initializers are **mandatory**; `x: number` alone is invalid.
- `:` is an optional **assignability constraint**. The initializer's inferred type must be equal to or assignable to the declared type.
- Any type expression, including a `where` refinement, may appear after `:`. For example, `x: number where n => n > 0 = 5` requires the initializer to satisfy that restricted type (TYP-REF-11).
- A constraint **does not widen** or overwrite the inferred type. Thus `x: number = 42` still has inferred type `42`.
- The `&` operator is reserved for type **intersections**, not type constraints.

## Immutability, redeclaration, and scope

Each declaration creates a **new immutable binding**. Reusing the same identifier, including in the same scope and with an unrelated type, is valid. The newest visible binding shadows earlier bindings; it never mutates them.

```natcode
x = 10
x = x + 5           // initializer sees previous x; new x = 15
x: string = "hi"    // new binding; previous x remains immutable
```

A declaration's initializer resolves a same-name reference to the **previously visible** binding. This holds both for a same-scope redeclaration and when a declaration shadows a binding in an outer lexical scope.

```natcode
x = 10
getInner = () =>
    x = x + 1        // inner x = 11
    x
result = x           // outer x remains 10
```

The lambda syntax is illustrative; code blocks are **indentation-defined** rather than brace-delimited (see [syntax-and-types.md](spec/syntax-and-types.md#code-blocks-and-data-structures)).

- Visibility is **sequential**: ordinary declarations become visible to later declarations, not earlier ones.
- Functions may be **self-recursive**, as an explicit exception to the ordinary visibility rule.
- A function's references to outer names resolve to the **specific bindings visible at the function's definition**, rather than a later same-name redeclaration or the caller's scope.

```natcode
x = 10
getX = () => x
x = 20
result = getX()       // 10
```

- Local declarations may shadow imported identifiers as well; this is distinct from duplicate *imported* bindings, which are an error.

## Identifier categories

- Ordinary value bindings use Haskell-style **lowercase-leading** names, including Unicode letters supported by Unicode identifier categories, or emoji identifiers.
- Types and constructors use **PascalCase** and cannot use emoji identifiers.
- Namespaces introduced by imports must use **PascalCase**.
- **Top-level values** may *also* use `UPPER_SNAKE_CASE`; this is **allowed but not required**. Types/constructors may not use `UPPER_SNAKE_CASE`. Ordinary local values do not gain this exception.
- A standalone `_` is reserved as a wildcard, not an ordinary binding identifier.
- Unicode emoji sequences are valid value names, including composed emoji such as `👩‍💻`. Which emoji sequences are admitted is LEX-ID-04.

```natcode
maxSize = 100
MAX_SIZE = 100         // allowed at module top level
🚀 = 42
unique type Point(number, number)  // positional nominal constructor declaration
```

## Identifier mangling and compilation

Identifiers unsupported by a target language (e.g., emoji) are mapped to generated, target-safe identifiers. Name generation must be **collision-safe**. Source names and internal symbol identities remain available for correct resolution and debugging. The exact output spelling is not part of source-language syntax.

## Exact type inference

- Direct primitive literals infer their exact literal types: `42`, `"Alice"`, `true`, rather than automatically widening to `number`, `string`, `boolean`.
- Supported core constant operations infer exact literal results deterministically as part of typing: `40 + 2` infers `42`. Optional evaluation of a user-defined call must not change its inferred type (TYP-LIT-02, TYP-EVAL-01).
- A binding's optional `:` constraint does not erase this precision.
- Precise rules for function return inference and evaluation are recorded in [evaluation.md](spec/evaluation.md); they don't affect basic variable syntax.

## Declaration grammar (schematic)

```ebnf
variableDeclaration = valueIdentifier, [":", typeExpression], "=", expression ;
```

The `valueIdentifier` category depends on scope: top-level `UPPER_SNAKE_CASE` is additionally permitted. The lexical grammar is in [lexical.md](spec/lexical.md); expression and type grammars are PAR-EXPR-01 and PAR-TYPE-01.

# Modules, imports, exports, and program entry

Item status and open questions for this file are tracked in the [parser](scorecards/parser.md), [resolver](scorecards/resolver.md), [types](scorecards/types.md), and [runtime](scorecards/runtime.md) scorecards.

## What is a module?

A module is a **logical, lexically scoped collection of declarations** with its own namespace and an import/export boundary. Its conceptual role is distinct from a package and from a physical file. For Natcode's initial source layout, **each `.nat` source file defines exactly one module**; no explicit module declaration is required.

A source file permits **top-level declarations only** (including imports and the terminal export declaration), not standalone executable expressions. A top-level variable initializer is part of a declaration, not a standalone statement.

Functions associated with types, future extension functions, and constructor-like functions may live in separate file modules and be connected through the import/export and future type-association system. Their syntax and resolution are PAR-EXT-01 and RES-EXT-01.

## Module form

All imports must precede other declarations. Every module must have **exactly one** `export` declaration **at the end** of the module, with nothing declared after it.

```natcode
from "./math" import { PI }

area = PI * 5 * 5

export { area }
```

- `export {}` is required for a library exposing no names.
- A module cannot combine a function entry export with an ordinary object export or have multiple terminal exports.

## Exported kind: object library or function executable

The final export may be an **arbitrary expression**, but its inferred type must statically establish exactly one category:

- **Object** → importable **library module**.
- **Function** → **executable module**, with that function as the program entry point.
- **Primitive or directly exported type** → invalid. Types and primitive values must appear as **properties of an exported object**.
- **Expression potentially returning either object or function** → compilation error; module kind cannot depend on runtime outcomes.

```natcode
PI = 3.14159
square = x => x * x
export { PI, square }        // library: object-shaped public interface
```

```natcode
run = () => print("Hello")
export run                   // executable: function entry
```

```natcode
api = { PI: 3.14159, square: x => x * x }
export api                   // same public interface as export { PI, square }
```

Here `export { ... }` builds the module's exported object. `export api` where `api` is an object exposes its **properties as named exports**, not one implicitly named `api` export. Object literal property colons are approved (PAR-OBJ-02); the remaining object-literal grammar is PAR-OBJ-01. Function body grammar beyond the approved brace-delimited block boundary remains PAR-FN-01 and PAR-BLK-02.

- Both **types and values** can be placed in the same exported object; `export { Point, origin }` is valid.
- A module may **re-export previously imported declarations**, including complete imported namespace values.
- Object properties' **public names must be unique** within the exported interface. Unlike same-scope variable redeclarations, duplicate public export keys are compilation errors.
- **Export aliases** use `=` with the public name on the left: `export { publicName = localName }`.

```natcode
from "./math" import { square }
export { squareNumber = square }
```

## Entry modules

- An executable is selected by **source-file path**, allowing multiple executable files in the same project; command shape `natcode run src/main.nat` is illustrative.
- An executable module is **not importable** by other modules.
- Its entry function can be **imported from a library module**; it need not be declared locally.
- Each module has only one terminal export, so an executable module has one entry function.
- The **entry function's parameter shape, effect/purity model, and runtime context** are RUN-ENTRY-01. There is no mandated `main` name.

```natcode
// app.nat
run = () => print("Hello")
export { run }               // library

// main.nat (different file)
from "./app" import { run }
export run                   // executable
```

## Import syntax and ordering

Natcode uses **file-first syntax**:

```natcode
from "./math" import Math
from "./math" import { PI, square }
from "./math" import *
from "./math" import { PI }, Math
```

- `Math` is a **PascalCase namespace alias**.
- `{ PI, square }` imports named exports as direct local bindings.
- `*` imports **all possible exported names** as direct local bindings; `_` is **not** an import wildcard.
- The combined form `{ PI }, Math` imports `PI` directly and places only the **remaining** names in `Math`; `Math.PI` is absent from that combined import.
- The designer also wants remaining exports to be importable unqualified via wildcard in a combined selective import; the grammar for this is PAR-IMP-08.
- Import aliases use `=` with local alias on the left: `from "./math" import { localName = publicName }`.
- Bare `from "./math"` without `import ...` is **invalid**.
- Multiple import declarations from the **same module are allowed** and resolved independently. For example, separate `{ PI }` and `Math` imports leave `PI` inside `Math`; one combined `{ PI }, Math` import removes `PI` from that `Math` view.

## Paths and dependencies

- Ordinary import paths must be **static string literals**, not computed expressions or runtime variables.
- Local imports use explicit relative prefixes `./` or `../`, resolved against the importing file.
- `.nat` can be omitted for Natcode source modules; non-Natcode formats (such as `.json`) use an explicit extension.
- Direct imports of **JSON** are supported in principle; their value representation is RES-MOD-08. Other non-Natcode file types are RES-MOD-09.
- Built-in and external package path schemes are RES-MOD-07.
- **Circular module dependencies are forbidden**, including cycles through several modules; the compiler reports an error.

## Import names and shadowing

- Two imports that introduce the **same local identifier** are a **compilation error**, even if imported from the same module, even if they identify the exact same source binding, and even if unused.
- Different aliases or namespaces may be used to disambiguate.
- This is not inconsistent with ordinary binding redeclaration: a later **local declaration can shadow an imported binding** according to Natcode's immutable sequential scope rules.

```natcode
from "./math" import { MATH_PI = PI }
from "./geometry" import { GEO_PI = PI }

PI = 3.14    // allowed local declaration
```

## First-class namespaces and persistent updates

Namespace imports are **first-class immutable values**, not compile-time-only symbols. They can be assigned, passed to functions, returned, and nested in other objects and namespaces.

Multiple imports of the same module initially reference the **same logical exported namespace value**. An update such as `Math.PI = 3.14` constructs a **new immutable namespace value** for the current binding rather than mutating the shared original. Other references and previously captured values retain the older version. Persistent data structures and structural sharing are intended implementation techniques; detailed dotted-update syntax and semantics are PAR-UPD-01 and RUN-UPD-02.

## Exported object shapes and optional properties

- The exported object may have multiple possible statically inferred shapes (e.g., a union of object types).
- The compiler must statically enumerate the **finite set of possible public property names**, but the presence and values of each property can vary at runtime.
- A named import is legal when the property exists in **at least one** possible export shape. If absent in some branches, its inferred type includes a `None` case.
- Importing a property that exists in **no** possible export shape is a compile-time error.
- Wildcard imports include the **union of all possible export names**, even conditionally present ones.
- No `null` or `undefined` values are intended for Natcode. The exact semantics and spelling of `None` are TYP-NONE-01.
- A dynamic object with arbitrary runtime keys may be exported **inside a statically named property** (e.g. `export { data }`); arbitrary unenumerable runtime keys are not allowed as the module's top-level public export interface.

```natcode
// api.nat (illustrative conditional syntax)
export if condition then
    { x = 10, y = 20 }
else
    { x = 30, z = 40 }
```

```natcode
// consumer.nat
from "./api" import *
// x: 10 | 30
// y: 20 | None
// z: 40 | None
export {}
```

## Lazy module evaluation

- Importing a module does not eagerly evaluate all its top-level values.
- Bindings are evaluated on first demand and **memoized** (call-by-need).
- Exported object properties are independently lazy; accessing one property does not evaluate another unrelated property.
- Arbitrary factory expressions can produce exported objects, and deferred function bodies may expose lazily computed members. Lowering this through arbitrary function calls, and the purity/effect boundary, are RUN-LAZY-05.

```natcode
export { cheap = 42, expensive = expensiveCalculation() }
// Accessing cheap does not force expensiveCalculation().
```

# Type inference, lazy evaluation, and debugging

Item status and open questions for this file are tracked in the [types](scorecards/types.md), [runtime](scorecards/runtime.md), and [debugger](scorecards/debugger.md) scorecards.

## Literal precision

- Literal expressions have exact literal types by default.
- Supported core constant operations infer exact types deterministically: `40 + 2` infers `42`. This is a static typing rule, not the result of optional optimization.
- Type constraints (`:`) check assignability without widening.

## Function return inference: context-independent

The designer revised an earlier broader constant-evaluation proposal: **function return types are inferred from parameter types and the function's own body**, not specialized using the specific values passed at each call site, nor values outside the function. Exact types can propagate through function-local variables.

```natcode
// Illustration of intended syntax and inference:
test(x: number) => x * 2   // return: number
test(x: 24) => x * 2       // return: 48
```

The function syntax in these examples is illustrative (PAR-FN-01, TYP-FN-03); they illustrate type inference rules only.

Optional compile-time evaluation must not change inferred types, runtime semantics, or whether a program is valid (TYP-EVAL-01). Pure functions with statically known inputs may be evaluated at compile time to validate mandatory `where` restrictions (TYP-EVAL-03). A restriction proven false is a compile error, and required validation cannot silently fall back to a broader type. If the compiler cannot establish a mandatory restriction, that is also a compile error; unknown is not treated as either true or false (TYP-EVAL-04). Exact evaluation budgets and the complete eligibility rules for compile-time function evaluation remain open (TYP-EVAL-02).

## Flow-sensitive refinement and symbolic reasoning

Natcode carries facts established by control flow into type checking (TYP-EVAL-05). A successful Boolean condition refines the bindings used by that condition inside its branch, while later branches also learn from the conditions that previously failed.

For example, with:

```natcode
type Positive = number where
    x => x > 0
```

inside a branch guarded by `x > 0`, `x` is known to satisfy `Positive`. If a previous branch tested `x > 0` and did not run, the remaining path knows that condition is false. With ordered numeric values, after excluding both `x > 0` and `x < 0`, the remaining path can refine `x` to `0`.

Refinement facts compose through Boolean conjunction, disjunction, and negation. Pure named predicates also contribute facts: when a restriction is defined by a pure predicate, a branch in which that same predicate is known true may establish membership in the restricted type. Destructuring a restricted constructor preserves the facts that apply to its extracted parameters (TYP-REF-08).

The initial symbolic solver must guarantee a practical decidable subset of numeric reasoning (TYP-REF-10):

- equality and ordered comparisons between values;
- Boolean combinations of those relations;
- transitive implications such as `x > y` and `y > 0` implying `x > 0`;
- linear arithmetic with known constant coefficients, such as `x + 5 > y`, `x - y <= 10`, and `2 * x > y`.

Predicates outside that guaranteed symbolic subset remain valid. Multiplication or division between two unknown values, powers, and other nonlinear relationships are not required to be proven symbolically in the initial solver. When all relevant inputs are statically known, ordinary pure compile-time evaluation may still validate such a predicate directly.

A failure to prove a fact outside the supported solver is **not** proof that the fact is false. It simply cannot satisfy a mandatory static restriction unless another known fact establishes it. When the source value is already statically compatible with a restricted target's validation input type, `as?` may explicitly perform the remaining membership check as runtime validation (TYP-REF-12). Its result type remains `Target | ValidationError` even if compile-time evaluation or symbolic reasoning can prove the particular application will succeed or fail; such proof may eliminate runtime work but does not alter the validator's stable signature (TYP-REF-13).

## Diagnostics

Violated or unestablished mandatory guarantees are compile errors; provably redundant but valid code may warn; unsuccessful optional analyses need no diagnostic. Warnings do not prevent compilation or change semantics (TYP-DIAG-01).

Natcode diagnostics should be understandable without compiler or type-theory terminology (TYP-DIAG-02). When possible, an error should explain in ordinary language what the developer wrote, why Natcode cannot accept it, and what form would work instead. Invalid `where` forms are hard compile errors with source spans, and a concrete rewrite should be shown when the compiler can confidently provide one. Whether a valid `as?` whose success or failure is already statically known should produce an informational or warning diagnostic remains open (TYP-DIAG-03).

## Error handling

Natcode has no language-level exceptions, throwing/catching semantics, or exception-based propagation (RUN-EFF-04). Recoverable errors are represented explicitly as values. `try`, `catch`, and `throw` are not built-in exception constructs (LEX-KW-11).

Error values are ordinary first-class values, but their types are designated as errors and recognized by the type checker (TYP-ERR-02). Operations may produce a success value or an error value directly as alternatives in a union, without mandatory `Ok` and `Err` wrappers. For example, `number | ParseError` can represent either a successful number or a designated parse error (how error types are designated remains open).

`ValidationError` is the designated error alternative produced by explicit restricted-type validation with `as?`; it captures type-level validation failures while preserving the requested target as the success alternative (TYP-REF-12, TYP-REF-15). Its exact payload/message representation remains open (TYP-REF-16).

How types receive the general error designation, how possible errors are inferred in other signatures, and how errors are propagated and handled remain open (TYP-ERR-01). Unrecoverable runtime faults and failures in lazy computations remain a separate question (RUN-EFF-02).

## Laziness

- Top-level module bindings and exported object members are call-by-need and cached after evaluation.
- Unused work should not execute, regardless of whether the enclosing object originates in an expression or factory function, subject to actual data dependencies.
- Persistent immutable data structures allow versions to share storage; memoization avoids repeated computation. These are complementary, not synonymous.

## Debugging

Debug builds **preserve the language's lazy semantics**. Debugging tools may show suspended computations and let the developer explicitly force/step into them. Automatically evaluating every function in debug mode is rejected, because it changes program behavior. Production builds may remove unused pure computations and debug builds may retain richer source metadata.

The debugger interface, effects, resource limits, and force semantics are DBG-API-01.
